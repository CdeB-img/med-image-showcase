1. INVARIANTS ABSOLUS
===============================================================================

Le nouveau contrat doit préserver :

SINGLE_ATTEMPT_FAIL_CLOSED

REQUEST_PREPARED before provider transport

COMPLETED after provider response

strict record/replay

no client-controlled budget

Aucune nouvelle session ne doit pouvoir recréer un budget.

Invariant principal :

SUM(all committed cost across every session in campaign)
+
conservative_upper_bound(next_call)
<=
campaign_absolute_hard_bound

===============================================================================
2. CAMPAGNE ≠ SESSION
===============================================================================

Séparer explicitement :

CAMPAIGN_ID
SESSION_ID
PROJECT_ID
LOGICAL_CALL_ID

CAMPAIGN_ID possède :

- politique budgétaire ;
- cumulative measured cost ;
- cumulative committed upper bound ;
- campaign lifecycle ;
- campaign evidence root ;
- allowed provider contract ;
- immutable safety configuration.

SESSION_ID possède :

- identité conversationnelle ;
- Project ;
- turns ;
- appels propres à cette session ;
- provenance locale.

Une campagne peut contenir plusieurs SESSION_ID distincts.

Une SESSION_ID appartient à UNE seule campagne.

Changer SESSION_ID :

NE DOIT PAS
- reset le budget ;
- reset la preuve ;
- recréer un hard bound ;
- autoriser un retry ;
- effacer les consommations précédentes.

===============================================================================
3. POLITIQUE DE CAMPAGNE SERVER-SIDE
===============================================================================

La politique doit être :

- définie côté serveur ;
- explicite ;
- liée au CAMPAIGN_ID ;
- figée avant le premier appel ;
- persistée avec les preuves ;
- non modifiable par le body navigateur ;
- non modifiable après première dépense.

Contrat minimal :

CAMPAIGN_POLICY = {
  campaignId,
  maxSessions,
  measuredSoftStopUsd,
  absoluteHardBoundUsd,
  singleAttemptPolicy,
  allowedProviderModels,
  createdAt,
  policyDigest
}

Pour la future acquisition :

maxSessions = 5

measuredSoftStopUsd = 3.00

absoluteHardBoundUsd = 10.00

Ces valeurs sont une configuration de campagne explicitement autorisée,
pas de nouveaux defaults globaux du produit.

Le mode normal et les anciens canaries doivent conserver leurs contrats
historiques.

===============================================================================
4. PAS DE RESET DE BUDGET
===============================================================================

Tester explicitement :

SESSION_A
→ coût engagé

puis :

SESSION_B
→ le cumul avant premier appel B inclut intégralement SESSION_A.

Même exigence pour C/D/E.

Interdire notamment :

- nouveau recorder = nouveau budget ;
- nouveau browser = nouveau budget ;
- nouveau Project = nouveau budget ;
- nouveau sessionId = nouveau budget ;
- restart process = nouveau budget ;
- relecture partielle du journal = nouveau budget.

Le budget appartient à CAMPAIGN_ID.

===============================================================================
6. CONCURRENCE
===============================================================================

Deux sessions peuvent théoriquement tenter un appel en même temps.

Le budget global doit donc être sérialisé au niveau campagne.

Tester :

SESSION_A call
||
SESSION_B call

Résultat attendu :

- une seule admission critique à la fois ;
- la seconde voit la réservation de la première ;
- impossible de dépasser le hard bound par race condition.

Ne pas utiliser uniquement un verrou par session.

===============================================================================
7. PREUVES MULTI-SESSION
===============================================================================

Le stockage doit permettre de distinguer :

campaign
→ session
→ turn
→ logical call

tout en conservant un ledger global.

Exemple conceptuel :

campaign-X/
  campaign-policy
  campaign-ledger
  session-A/
    exchanges
  session-B/
    exchanges
  session-C/
    exchanges
  session-D/
    exchanges
  session-E/
    exchanges

Ne pas créer une seconde vérité budgétaire.

Le ledger campagne est propriétaire du cumul.

Les journaux session fournissent la provenance des appels.

===============================================================================
8. COMPATIBILITÉ HISTORIQUE
===============================================================================

Ne jamais réécrire les preuves des canaries précédents.

Le contrat mono-session historique reste interprétable.

Une ancienne campagne :

- ne devient pas multi-session rétroactivement ;
- ne reçoit pas les nouveaux plafonds ;
- ne peut pas être reprise avec une policy différente.

Les nouveaux comportements doivent être explicitement activés par une nouvelle
CAMPAIGN_POLICY.

===============================================================================
9. BUDGET CONFIGURABLE MAIS BORNÉ
===============================================================================

Ne pas remplacer 1/6 par 3/10 comme constants globaux.

Permettre une policy bornée par campagne.

La configuration doit être validée avant première dépense.

Interdire :

- valeurs négatives ;
- soft > hard ;
- hard inconnu ;
- changement après première préparation ;
- changement après première réponse ;
- configuration client ;
- configuration partielle silencieuse.

Les limites autorisées doivent être explicites.

Ne pas construire une plateforme de billing générale.

Le mécanisme reste un garde expérimental/local de campagne provider.
