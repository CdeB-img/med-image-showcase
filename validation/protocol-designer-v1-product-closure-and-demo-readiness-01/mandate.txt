===============================================================================
0. OBJECTIF
===============================================================================

L'objectif n'est plus d'améliorer abstraitement le moteur scientifique.

L'objectif est d'obtenir une V1 Protocol Designer réellement démontrable à
un chercheur, une DRCI, Bpifrance ou un partenaire institutionnel.

À la fin de cette mission, un utilisateur doit pouvoir vivre un parcours
cohérent :

NEW / EXISTING RESEARCH PROJECT
→ STANDARD CONVERSATION
→ UNDERSTANDING
→ HUMAN REVIEW
→ CANONICAL RESEARCH PROJECT
→ SCIENTIFIC ITERATION
→ DOCUMENT GENERATION
→ ADMINISTRATIVE COMPLETION
→ DOCUMENT REGENERATION
→ PERSIST
→ CLOSE
→ REOPEN
→ CONTINUE

Ne pas déclarer une capacité sans la démontrer par le produit réel.

===============================================================================
4. CIBLE V1 À IMPLÉMENTER
===============================================================================

Construire uniquement ce qui manque pour ce corridor :

A. PROJECT WORKSPACE

Un utilisateur doit pouvoir :

- créer un projet ;
- lui donner au minimum un titre temporaire ;
- voir ses projets existants ;
- ouvrir un projet ;
- revenir à la liste ;
- reprendre un projet existant.

Plusieurs Research Projects doivent pouvoir coexister sans contamination.

===============================================================================

B. PERSISTENCE

Le Research Project, ses décisions, versions et éléments nécessaires à la
conversation doivent survivre :

- refresh ;
- fermeture/réouverture de l'écran ;
- nouvelle session locale selon le mécanisme V1 retenu.

Pour cette V1 de démonstration :

ne pas construire une infrastructure SaaS complexe si une persistence locale
ou backend existante qualifiée permet de démontrer correctement le contrat.

Mais ne pas simuler la persistence dans le seul state React.

===============================================================================

C. PROFIL ET MÉTADONNÉES ADMINISTRATIVES

Prévoir deux niveaux explicitement distincts :

USER / ORGANIZATION PROFILE
réutilisable entre projets

et

PROJECT-SPECIFIC ADMINISTRATIVE DATA / ACTOR ROLES

Ne jamais injecter firstname/address/etc. comme science dans Research Project.

Réutiliser ActorRefs / organization refs / rôles existants lorsqu'ils existent.

Le formulaire doit distinguer :

REQUIRED
OPTIONAL

Pour les champs optionnels, expliquer brièvement pourquoi l'information peut
être utile, notamment pour préremplir les documents.

Ne pas exiger les données administratives avant de permettre au chercheur de
travailler scientifiquement.

===============================================================================

D. DOCUMENTS AVEC PLACEHOLDERS

L'utilisateur doit pouvoir obtenir un document même lorsque certaines données
administratives manquent.

Deux parcours :

1.
GENERATE_NOW

→ document concret
→ placeholders explicites pour informations absentes
→ statut :

DRAFT_WITH_PLACEHOLDERS

2.
COMPLETE_INFORMATION_FIRST

→ formulaire
→ complétion
→ génération

Les placeholders ne doivent jamais être inventés.

Exemples :

[Investigateur principal à compléter]
[Numéro de version à compléter]
[Promoteur à compléter]

selon les besoins réels du template.

===============================================================================

E. RÉGÉNÉRATION

Après :

- modification scientifique adoptée ;
- modification méthodologique adoptée ;
- ajout de données administratives ;

l'utilisateur doit pouvoir régénérer le document depuis l'état courant du
Project.

Ne jamais modifier manuellement le document comme nouvelle source de vérité.

PROJECT CURRENT STATE
→ DOCUMENT PROJECTION

===============================================================================

F. DOCUMENT RÉEL

Au moins UNE famille documentaire importante doit être réellement démontrable
end-to-end.

Préférer la famille déjà la mieux implémentée / câblée.

Ne pas développer dix documents médiocres.

Objectif minimal :

un protocole/synopsis/document d'étude suffisamment substantiel pour être
montré à un chercheur.

Il doit contenir du contenu issu du Project réel et non une fixture.

===============================================================================
5. AUTHENTIFICATION
===============================================================================

Ne pas construire un système complet d'authentification si celui-ci n'existe
pas et n'est pas nécessaire à la démonstration V1.

Pour la démonstration, la priorité est :

MULTI_PROJECT
PERSISTENCE
PROFILE
DOCUMENTS

Si une abstraction utilisateur existe déjà, la réutiliser.

Si une authentification complète constitue un chantier indépendant important :

la reporter explicitement.

Ne jamais construire un faux système de sécurité présenté comme production-ready.

- refus ;

- modification ultérieure.

Ne pas écrire le scénario pour satisfaire le parser.

10. QUALITÉ PRODUIT
===============================================================================

La démonstration ne doit pas montrer au chercheur des détails d'architecture
interne inutiles.

Standard Mode reste la surface principale.

L'expérience attendue :

COLLEAGUE_SCIENTIFIC
PRECISE
PROACTIVE
NATURAL_CONVERSATION

Les contrôles structurés servent à accélérer les décisions, pas à remplacer
la conversation.

Traiter comme MATERIAL :

- perte du Project ;
- contamination entre Projects ;
- décision non adoptée apparaissant comme adoptée ;
- document construit depuis un état périmé ;
- placeholder inventé ;
- disparition silencieuse d'une information ;
- réouverture incohérente ;
- génération documentaire fictive ;
- dead end visible dans le corridor principal.

14. REVUE CONTRADICTOIRE ULTRA
===============================================================================

- persistence uniquement apparente ;
- données partagées entre Projects ;
- document utilisant un Project stale ;
- metadata administratives injectées dans la science ;
- science stockée dans profil global ;
- placeholder remplacé par invention ;
- document modifié indépendamment du Project ;
- perte de provenance ;
- perte de version ;

- UI qui nécessite des manipulations Expert pour le parcours normal ;
- implémentation spécifique au scénario cardio ;
- nouvelle abstraction inutile.

Corriger uniquement les défauts démontrés.
